# 前端体验计划 · AI Software Video Studio

> 阶段：Frontend-First Experience Validation v0.1｜日期：2026-11-15
> 文档性质：本阶段的体验与范围基线。实现结果以运行中的产品为准，不以本文为完成声明。

## 1. 产品理解

### 1.1 核心目标

AI Software Video Studio 不是"输入一句话生成视频"的工具，而是一条**从可信软件事实到可审阅视频**的生产线：

```text
软件事实（文档 / PR / 运行界面 / 验证证据）
  → AI 理解（功能目录 + Claim + Evidence）
  → 人的确认与纠正
  → 视频策划（Brief / 脚本 / 分镜）
  → 真实演示录制（未来）
  → 可编辑工程 → 审核 → 导出
```

北极星是"每周通过事实审核、可复用的视频草稿数"。它要求产品同时具备三种能力，缺一不可：

1. **理解**：让用户能判断 AI 是否真的理解了自己的软件；
2. **控制**：让用户能修改事实、卖点、脚本、镜头，而不是接受一次性生成结果；
3. **可信**：每条对外声明都能追溯到证据和审核状态。

### 1.2 主要用户

| 角色 | 首要任务 | 最怕什么 |
|---|---|---|
| 产品负责人 / PM | 从版本变化中挑出值得宣传的功能，快速产出更新视频 | AI 把未上线或内部改动说成新功能 |
| 市场 / 内容运营 | 高频、稳定地产出多版本内容 | 每次都从零开始，工具不听话，画面不专业 |
| 开发者 / 开发负责人 | 用最低权限接入仓库，确认演示真实 | 授予过度权限、虚假宣传、录屏泄露数据 |
| 视频负责人 / 设计 | 审阅脚本与成片，局部修改，保持品牌一致 | 只能全片重新生成，无法精修，无法审核声明 |
| 售前 / 客户成功 | 针对具体功能生成可复用演示 | 演示不稳定、内容与真实产品不一致 |

### 1.3 关键用户旅程

主旅程（本阶段必须闭环）：

> 进入工作室 → 创建项目 / 模拟接入 → 查看并纠正 AI 理解 → 选择功能 → 创建视频 → 与 AI Director 协作 → 确认脚本 → 编辑分镜 → 模拟生产 → 在编辑器里修改并预览 → 审核事实与内容 → 模拟导出。

次旅程：

- **版本更新视频**：从 Release / PR 时间线选择范围 → 自动带出受影响功能与证据缺口 → 创建 30 秒更新视频。
- **品牌与配置维护**：修改 Brand Kit → 视频模板、项目卡、导出默认值同步变化。
- **异常处理**：证据过期 → 审核阻断 → 回到 Knowledge 重新验证 → 重新生成 / 审核。
- **生产异常**：录屏步骤失败 → 查看日志与错误 → 重试成功或取消；审批 Gate 暂停 / 恢复。

## 2. 本阶段要验证的核心假设

| # | 假设 | 前端如何验证 | 失败信号 |
|---|---|---|---|
| H1 | 用户愿意先纠正 AI 理解，再制作视频 | Knowledge 中结构化功能、证据、待确认建议是否易读易改；纠正是否影响下游 | 用户只看摘要，无法判断对错，或修改入口埋得太深 |
| H2 | 聊天不是 AI 视频协作的最佳主界面 | Director 以 Brief / 脚本 / 分镜结构为主，聊天只发起可验证的操作并展示影响 | 用户不断说话却不知道数据是否变化 |
| H3 | 分镜级编辑已能提供"可控感" | Storyboard 与 Editor 修改后预览、时长、总时长、审核立即同步 | 编辑器只是静态图，或修改不落到工程 |
| H4 | 确定性生产状态机足以建立信任 | 步骤、依赖、日志、失败、重试、审批都可观察、可控 | 用户以为进度条是装饰，或无法解释失败 |
| H5 | "模拟"标注不会破坏体验 | 所有 Demo / 模拟能力有统一、克制、可理解的标识 | 用户误以为已连接真实 GitHub / 已渲染 MP4 |
| H6 | 单一 Demo 项目足以支撑完整评估 | Lumen Analytics 提供功能、PR、Release、证据、素材、工程、运行记录 | 需要跨项目借数据才能完成流程 |

## 3. 体验策略

1. **事实优先于画面**：Knowledge 是产品的心脏；视频页面随时能看到某句话来自哪个功能、哪条 Claim、哪份证据。
2. **结构优先于聊天**：AI Director 是"导演工作台"，聊天只是操作入口之一。每次 AI 操作都要展示"改了什么、影响哪些镜头、总时长如何变化"，且可撤销。
3. **渐进披露**：创建视频先问目标与内容，高级选项折叠；默认值必须可解释且合理。
4. **局部修改，全局同步**：分镜、时长、字幕、品牌改一处，Storyboard / Editor / Review 同步；删除卖点同步移除对应镜头。
5. **诚实是体验的一部分**：Demo 数据、模拟连接、模拟生产、模拟导出在界面上明确区分；不生成假 MP4、不伪造 GitHub 结果。
6. **专业但克制**：深色工作室质感，统一的设计系统，关键操作明显；避免渐变堆叠、无意义统计卡、到处发光的"AI 味"。

## 4. 范围与优先级

### 4.1 本阶段 P0（必须可操作）

| 模块 | 体验目标 | 优先级 |
|---|---|---|
| 应用框架 / 导航 / 设计系统 | 像成熟 SaaS，而不是组件演示 | P0 |
| Dashboard | 用户知道"现在该做什么" | P0 |
| Onboarding | 4 种接入方式、分步、返回、校验、状态保持 | P0 |
| Knowledge Center | 结构化功能、Claim/Evidence、纠正、待确认建议 | P0 |
| Video Creation Wizard | 4 种模式、合理默认、实时反馈、创建工程 | P0 |
| AI Director | 结构化策划 + 真实生效的对话操作 | P0 |
| Storyboard Studio | 编辑、排序、增删、时长、证据、状态 | P0 |
| Video Editor | 时间驱动的预览、播放/拖动、编辑、撤销重做、持久化 | P0 |
| Production Monitor | 确定性状态机、失败、重试、审批、取消 | P0 |
| Review & Export | 事实检查、退回、批准、模拟导出、工程 JSON | P0 |
| Settings / Brand Kit | 品牌修改跨页生效、连接器状态、重置数据 | P0 |

### 4.2 本阶段明确不做

- 真实 OAuth、源码扫描、数据库、API、AI 模型、Mastra、Playwright 生产录制、FFmpeg / Remotion 服务端渲染、真实上传 / 发布、ATVG2。
- 通用多轨 NLE（无限轨道、关键帧曲线、专业调色、协作评论线程）。
- 真实 MP4 文件。导出 MP4 是**有状态的模拟任务**，不产生可播放文件；工程 JSON 与 SRT 是真实可下载文件。

## 5. 关键设计决策与取舍

### D1. 三层导航：Workspace → Project → Video

**方案**：全局首页保持跨项目视角；进入项目后有 Knowledge / Videos / Brand 项目导航；视频是独立工作区，拥有 Director / Storyboard / Editor / Production / Review 五个阶段。

**取舍**：比"十个平级页面"多一层上下文，但解决了"用户不知道自己在改哪个项目的哪条视频"的常见问题。路由与面包屑始终显示当前项目 / 视频。

### D2. Knowledge 是唯一事实源，视频引用 ID 而不是复制事实

**方案**：Feature / Claim / Evidence 存在统一领域层；Scene 只保存 featureId / claimIds。功能重命名后，新创建的视频与所有引用名称自动更新；已完成旁白中的旧文案不被悄悄篡改，但在审核页标出"事实快照"与证据状态。

**取舍**：比纯前端 mock 更复杂，但能验证"跨页面数据一致性"这一核心产品假设。

### D3. Director = 结构化计划 + 命令，不是开放聊天

**方案**：对话框中只支持可识别、可执行、可展示影响的操作（缩短、换语气、换受众、调序、重生成分镜、删除 / 添加卖点、改写旁白、换风格）。无法识别时明确说明模拟能力边界，并给出可点击的建议命令。

**取舍**：比自由聊天少一些"魔法感"，但用户能真正预测和控制结果，也避免伪造 AI 能力。

### D4. 编辑器采用"分镜级时间线 + 本地时间驱动预览"

**方案**：不建设通用 NLE。中间预览由当前时间实时计算场景、字幕和画面动效，支持播放、暂停、拖拽、镜头切换；底部时间线按真实时长比例布局。

**取舍**：不能导出真实视频，但足以验证"修改是否立即被感知"与"时长 / 顺序 / 字幕是否一致"。

### D5. 生产是确定性状态机，不做随机假进度

**方案**：固定 DAG（知识分析 → Claim 验证 → 脚本 → 分镜 → 录屏 → 配音 → 合成 → QA），固定耗时，人为选择场景（成功 / 录屏失败重试 / 审批 Gate）。暂停、继续、取消、重试、审批均改变真实本地状态。

**取舍**：不如随机进度"像真的"，但可重复测试，也能暴露真实产品必须处理的异常。

### D6. 四项能力全部标为"模拟"，并提供统一说明入口

**方案**：顶部常驻"演示模式"；连接器显示"模拟连接"；生产步骤显示"模拟执行"；导出显示"模拟导出（不生成 MP4）"；Demo 数据在项目与知识页有标记。顶部说明面板列出真实 / 模拟边界。

**取舍**：牺牲一点"完成感"，换取评估时不被误导；这正是本阶段的目的。

### D7. 视觉方向：Cinema-grade dark studio，不用 AI 紫渐变

**方案**：墨黑底、暖白文字、荧光青柠主操作色、紫色仅用于 AI 语义标记；Space Grotesk 标题 + Inter 正文；细边框、低对比层次、少量颗粒与光晕。品牌色只进入"内容画布"，不污染工作台 UI。

**取舍**：比常规 shadcn 灰黑更有识别度，同时克制。

## 6. 现有文档中的冲突与处理建议

| # | 文档中的倾向 | 体验问题 | 本阶段处理 | 建议 |
|---|---|---|---|---|
| C1 | 01/09 建议从 Release Video 单点切入 | 容易把产品做成"PR 转视频"工具，无法评估完整 Studio | 首页与导航以完整 Studio 呈现，四种模式平权；Release 作为强入口而非唯一入口 | 正式 MVP 可以 Release 为楔子，但 IA 保留完整 D 形态 |
| C2 | 03/07 的编辑器包含多轨、局部重渲染 | 前端阶段成本高，易做成半成品 | 先做分镜级时间线 + 时间驱动预览，明确非 NLE | 后续按真实编辑需求增加轨道，不按竞品清单堆功能 |
| C3 | 02 的页面清单包含 Demo Lab / Video Library | 信息架构过平，用户认知负担高 | 将 Demo 能力收进 Production Monitor 的步骤详情；新增轻量 Video Library 作为项目资产视图 | 真实产品中 Demo Lab 独立成页需等录屏能力可用 |
| C4 | 06 的三道审批 Gate 与快速出片存在张力 | 每步都审批会让首次体验很重 | Gate 1（脚本）与 Gate 2（生产环境）在产品内体现为明确阶段确认；Gate 3 在 Review 落地；模拟中可跳过 Gate 2 | 正式产品要按风险分级，不要所有项目同一审批强度 |
| C5 | 08 要求零无证据公开声明 | 用户可能选到 stale claim，导致流程卡住 | 选择时警示，审核时阻断并提供"去重新验证"入口 | 保留阻断，不做"一键忽略"，这是产品信任的底线 |
| C6 | 05 的状态机非常细 | 前端全部呈现会过载 | 页面展示面向用户的状态（草稿 / 待审 / 制作中…），技术状态保留在领域层 | 对外文案避免直接暴露 status code |
| C7 | 09 要求所有结果附真实命令与证据 | 前端阶段无法提供真实后端产物 | 交付中明确"已验证 / 未验证"边界，不把模拟结果写成真实能力 | 保持同样的工程诚实标准 |

## 7. 前端架构

```text
apps/web-studio          React + Vite + Router + 应用外壳
libs/ui                  设计系统、通用交互、场景预览、应用骨架
libs/domain              领域类型、Zod Schema、时间线 / 状态纯函数
libs/mock-data           Demo fixtures、引导模板、资产与视频工程种子
libs/mock-services       确定性服务：Director / 生产引擎 / 接入 / 导出
libs/state               Zustand 领域 Store（持久化）+ UI Store
libs/features/project-hub   Dashboard / Onboarding / Knowledge / Library / Settings
libs/features/video-studio  Wizard / Director / Storyboard / Editor
libs/features/production    Production Monitor / Review & Export
```

依赖方向：`app → features → state/ui/domain`，`state → mock-services/domain/mock-data`，`ui → domain`，`domain → 无`。由 Nx + ESLint module boundaries 约束。

## 8. 成功标准

本阶段不以代码量或组件数衡量，而以以下问题能否被真实回答衡量：

1. 我能否在不看文档的情况下完成一次从项目到导出的完整旅程？
2. 我修改功能名 / 删除卖点 / 改时长 / 改字幕 / 改品牌色后，下游是否立即反映？
3. 刷新页面后，我是否还在原来的项目、工程和编辑结果里？
4. 当证据过期、录屏失败、审批未通过时，系统是否明确告诉我原因和下一步？
5. 我是否清楚哪些是真实可用的交互，哪些是模拟能力？
6. 在 1280 / 1440 桌面宽度下，编辑器与监控页是否仍可用？

验收细则见 `UX-ACCEPTANCE-CHECKLIST.md`。

## 9. 风险与待验证问题

- **数据一致性风险**：跨 Store 的派生数据若不集中计算，容易出现总时长、镜头数与审核状态不一致。对策：所有派生值由纯函数计算，不在组件里各算一套。
- **模拟感风险**：聊天回复若只改一句话，用户不会相信系统"理解"了。对策：每次操作必须伴随结构化 diff、影响范围与真实数据变化。
- **复杂度风险**：页面太多导致都只有 70 分。对策：先闭环主旅程，再做空 / 错 / 加载状态与边缘场景。
- **性能风险**：时间驱动预览若每帧触发全局 Store，会拖慢编辑器。对策：播放时间使用页面本地状态 / requestAnimationFrame，仅在提交编辑时写 Store。
- **后续真实化风险**：UI 直接依赖 mock 数据结构。对策：页面只通过 Store action 和领域类型交互；未来替换 mock-services 为 API client 时保留 action 契约。

## 10. 推荐后续（不在本阶段承诺）

1. 与 5–8 位目标用户做可用性测试，重点观察 Knowledge 纠正与 Director 命令是否符合心智。
2. 用真实 staging + Playwright 打通一条录屏，验证"演示断言成功"比"脚本结束"更可信。
3. 把导出 JSON 的工程 Schema 固化为版本化契约，接入 Remotion 预览。
4. 按真实使用频率决定是否需要多轨时间线，而不是按竞品功能表扩张。
